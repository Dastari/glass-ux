# Glass UX design rules

These rules are the shared contract between the library, the applications built with it and
the agents that write code for either. Tokens and component behaviour are the implementation
authority; the rules explain what they guarantee and what the host must do in return. An
application supplies its own data, routing, branding and policies.

Each rule has a stable number (R5.8). Code comments, specimens and reviews cite these numbers,
so a rule keeps its number when the text changes. "Must" marks a requirement; everything else
is the default to follow unless a project's instructions say otherwise.

## Screen content rules

These defaults apply to every website, application screen, demo and component composed with
Glass UX, including work generated by an agent. Follow them unless explicit user or project
instructions require different content. A deliberate article or long-form document may contain
the headings and prose its readers need; it is not a template for an application screen.

1. **Do not overuse subheadings.** Add a heading only for a distinct, useful information
   group. Do not stack an eyebrow, headline, subtitle and introductory paragraph that repeat
   the same point, or add a heading to every small piece of content.
2. **Do not add non-informational copy unless requested.** Use professional, factual labels
   and descriptions. Do not invent motivational, irrelevant, cheerful or promotional slogans
   such as “A happy place for all your components”, “A little slice of your own UI” or
   “Great Tools. Great UI”. A request to build a website with this library does not authorize
   this style of copy.
3. **Do not overexplain the page.** Omit large introductory blocks, feature summaries and
   paragraphs that narrate obvious controls. Explain only what the user needs to make a
   decision or complete a task. Put optional help beside the relevant control or in a
   disclosure.
4. **Do not push primary content down with unnecessary framing.** Keep useful content and
   actions near the top of the first screen, including on phones. Remove redundant headers,
   toolbars, navigation rows and paragraphs; put secondary navigation and settings in an
   appropriate drawer, sheet or disclosure.
5. **Do not repeat a route heading already supplied by navigation.** If a horizontal tab,
   breadcrumb or other visible route control clearly names the current view, start that view
   with its content. Do not print the same title or an introduction immediately below it.
   Preserve accessible names without adding duplicate visible framing.
6. **Do not move interaction targets through content shifts.** Reserve space for loading,
   validation, status, images and asynchronous results. Replace content in place. Do not
   inject banners, rows, menu items or other DOM content that moves a button or menu after
   the user has positioned the pointer, focused it or begun interacting. Loading completion,
   polling, hover and focus must not unexpectedly relocate controls. Deliberate navigation,
   disclosure and resizing may change content while preserving the activated control's
   anchor and focus.

Review the first viewport, headings and copy before adding decorative framing. Verify control
positions while delayed data, validation, fonts, images and status updates arrive; a static
screenshot or accessibility check does not establish layout stability.

## R1 · Consistency

- **R1.1** Use the same primitive for the same interaction: one Button, one Menu, one
  Segmented. Do not restyle a primitive into a look-alike of another.
- **R1.2** Define an entity's actions once (`defineActions`) and render that definition in its
  header, row menu, context menu, bulk bar and command palette.
- **R1.3** Reuse library compositions (EntityHeader, SettingRow, FactList, DataTable) before
  building a local one; extend through slots and props, not forks.
- **R1.4** Derived values are stable: the same input renders the same output, so nothing moves
  between renders (palette slots, generated colours, identity hues).

## R2 · Copy

- **R2.1** Say a thing once. A view does not repeat the label of the tab, breadcrumb or title
  that opened it, and a chart does not label a value its title already names.
- **R2.2** Subtitles and secondary lines carry data — an identifier, model or location — never
  a restatement of the title.
- **R2.3** No headlines, taglines or encouragement in product screens (see
  [screen content](#screen-content-rules)).
- **R2.4** Errors say what failed and what to do next: “Agent offline — retry when NST-C106
  reconnects”. Do not show raw transport or stack messages.
- **R2.5** Empty states state one fact (“No samples in the last hour”); while searching or
  filtering they name the query and offer to clear it.
- **R2.6** Library copy uses Australian English spelling. Numbers use tabular figures where
  they align in columns.
- **R2.7** Units follow numbers after a thin space (`12 GB`); relative times read naturally
  (“just now”, “3 min ago”) and never point into the future for past events.
- **R2.8** Help text appears only when the format or consequence is not obvious. Accessible
  names identify every control, including icon-only ones.

## R3 · Tokens and themes

- **R3.1** Colour, geometry, typography and motion use semantic tokens. Never hard-code a
  colour, length, radius or duration in component CSS; `pnpm tokens:check` enforces this.
- **R3.2** Variants are `data-*` attributes, not class names or inline styles.
- **R3.3** Status tones (success, warning, danger) mean status. Use them only while a value is
  in that state; a choice that is not a status uses the accent.
- **R3.4** A component picks a role token (`--radius-chip`, `--inset-panel`), never a scale
  step (`--radius-sm`). Roles let themes change geometry without touching components.
- **R3.5** An island (a tooltip, a brand mark) may re-declare the palette or mode for itself
  alone; it never changes tokens on an ancestor.
- **R3.6** Applications register palettes with `definePalette` and set defaults or locked
  preferences with `configureAppearance`. The default palette is Graphite.
- **R3.7** Respect the person's appearance choices: mode, palette, material, motion, density,
  UI scale, radius and line weight. Do not override them for one screen.
- **R3.8** Red belongs to danger and the accent to selection. Categorical colours (series,
  organisations, tags) avoid both.
- **R3.9** A level (Meter, MeterCell, Gauge) is neutral while healthy, so a calm page stays
  calm. Pass `tone="data"` to Meter or MeterCell only where the healthy level is the data
  being compared, such as a disk column; warning and danger still apply past the thresholds.

## R4 · Materials

Glass is more than blur. Every material carries a lit top edge, a shaded lower edge and, on
layers and cards, a soft inner lens glow. Interactive glass adds a specular highlight that
follows a fine pointer and a glint on the rim nearest it.

- **R4.1** Use the shared materials (`glass-chrome`, `glass-panel`, `glass-overlay`,
  `glass-float`, `glass-card`, `glass-control`, `glass-inset`) through components and Surface;
  never declare a `backdrop-filter`, fill or rim of your own.
- **R4.2** One blurred layer at a time. A layer never sits inside another layer; content inside
  a panel uses `control`, `inset` or `card` fills. An overlay rendered inside a layer takes an
  opaque fill automatically.
- **R4.3** Glass needs something to bend: put `canvas-ambient` (or `canvas-background`) on the
  application canvas. Glass over a flat colour reads as a grey box.
- **R4.4** Support Glass, Frosted and Solid. Frosted lowers the blur and raises every fill,
  controls and wells included. Solid, reduced transparency and browsers without
  `backdrop-filter` make every material opaque with the same geometry: no element filters
  the backdrop, and controls, wells, soft tints and skeletons take opaque fills, so the
  canvas never shows through. Only hover and press states, scrims and edge shading stay
  translucent. A surface may take its own level (Surface and Panel `glass`, or `data-glass`
  on any element) for itself and its contents, never more transparent than the page's: a
  person's Solid choice or reduced transparency still applies everywhere.
- **R4.4a** The application chooses how glass blurs, for every surface:
  `configureAppearance({ glassRendering })`. `live` (the default) blurs with backdrop-filter;
  `baked` gives panels and chrome on the page canvas a copy of the canvas blurred once, which
  looks the same and costs nothing per frame, and keeps the live blur for overlays and
  anything moving. Baked assumes panels and chrome sit on the canvas (R4.6, the layout
  contract); a layer that floats over content uses `glass-overlay` or `glass-float`.
- **R4.5** Elevation follows the material: chrome and panels are low, overlays and dialogs
  high. Do not add shadows to raise a component.
- **R4.6** Page framing — headings, breadcrumbs, group labels, toolbars over panels — sits on
  the canvas, not in a material.
- **R4.7** Anything over imagery (screenshots, media, vivid gradients) sits inside
  `.over-imagery`, which frosts fills and adds a halo to bare text and icons.
- **R4.8** Repeated cards in a long list use `glass-card`: the panel look without a blur pass.
- **R4.9** Lit controls (`fa-lit`) and pressable controls (`fa-pressable`) come from the shared
  recipes; the highlight never paints over text, and Solid keeps only the static rims.
- **R4.10** Print: the library's print layer (`src/styles/print.css`, part of the stylesheet)
  turns every material into a white surface with a hairline border, removes blur, canvas
  artwork and shadows, sets text near black with dark accent text, and lets the shell, panels
  and scroll containers grow so every page prints. It leaves out the rail, top bar, tab bar,
  section drawer, inspector, window dock, toasts, tooltips and scroll-edge hairlines; mark
  chrome that must print with `data-print="keep"` and anything else to leave out with
  `data-print="hide"`. Charts print in colour with their legends; charts, cards, tiles,
  setting rows and table rows avoid page breaks; a DataTable prints every loaded row (rows
  not yet loaded by paging or infinite scroll are not fetched); external links in long-form
  content (Markdown, rich text, `<article>`, `[data-print-links]`) print their address.

## R5 · Layout

- **R5.1** The shell owns the viewport; the document never scrolls. Each content area scrolls
  inside its own container, and a parent gives bounded content a definite height.
- **R5.2** The top bar holds the scope (organisation or workspace), the breadcrumb, search and
  account. The scope keeps its full name longest; changing scope resets the view to that
  scope's home.
- **R5.3** In a workspace everything is a window (R14); the workspace itself carries no glass.
- **R5.4** Conversations, documents and articles use the centred reading column
  (`--reading-column`); application views use the available width.
- **R5.5** Grids reflow with their container (auto-fill, minimum track size); never fix a
  column count.
- **R5.6** Prose stops at `--measure`.
- **R5.7** Only the edges a surface touches take safe-area insets.
- **R5.8** Separate groups with space, fills and labels, not dividers. A hairline marks a
  scroll edge only while content continues beyond it.
- **R5.9** Use Surface and Panel geometry props (`padding`, `radius`) and slots
  (`Panel.Header`, `Panel.Body`, `Panel.Footer`). A material class alone supplies no padding or
  corners; see the [layout contract](layout-contract.md).
- **R5.10** Do not wrap a group of panels in another panel to draw a frame.

- **R5.11** Component CSS uses logical inline properties (`padding-inline-start`,
  `inset-inline-end`, `text-align: start`) for reading-order layout. Directional icons and
  horizontal keyboard navigation follow the region’s direction. Physical coordinates are
  reserved for spatial content such as charts, maps and free windows.

## R6 · Navigation

- **R6.1** Level-one navigation is the Rail: icon-only, on the canvas, every item with a
  tooltip.
- **R6.2** Places are routes. Level-three sections, table sorting, filters and paging belong
  in the URL; component state is the exception for transient presentation choices.
- **R6.3** Only the routed view transitions between routes; the shell stays still.
- **R6.4** One breadcrumb, in the top bar, always at the same position.
- **R6.5** A view does not repeat the breadcrumb's last crumb as its title.
- **R6.6** Tabs that overflow move into a menu, and the active tab always stays visible.
- **R6.7** On phones the Rail becomes the TabBar, a floating pill above the safe area.
- **R6.8** Below the navigation's container threshold, a section rail becomes the horizontal
  tab strip (its overflow in More, R6.6), and section navigation may give way to the section
  drawer. Show a section drawer only when it holds real navigation.
- **R6.9** A setting inherited from a broader level (workspace → organisation → entity) shows
  where it comes from and which level enforces it. History is not filtered by scope switches.
- **R6.10** Routed tabs are places; local tabs and Segmented are presentation choices.
  Applications own URLs, navigation and scope changes.

## R7 · Container awareness

- **R7.1** Only the shell reads the viewport. Everything inside a surface uses container
  queries and measured boxes.
- **R7.2** The box decides a component's tier on both axes, never the device.
- **R7.3** Charts, maps, workspaces and virtualised tables are size containers: their parent
  must give them a definite height.
- **R7.4** Content gives way in a stated order and never clips silently: labels drop before
  values, secondary columns before primary ones, and a viewport pans rather than clipping.
- **R7.5** Every component must work in the container lab's five boxes, from a phone column to
  a wide desktop pane.
- **R7.6** A control with several forms collapses within the box it is given: Segmented steps
  from labels to icons to a menu, SwatchPicker from swatches to a menu. A toolbar must let its
  controls shrink so they see a constrained box, and must never overflow: use the `fa-fit-row`
  recipe and mark the order in which controls give way (`fa-fit-1` first).

## R8 · Text and figures

- **R8.1** Truncate single-line names and identifiers with `TruncatedText`; the full text
  appears in a tooltip only when it was cut.
- **R8.2** Wrap prose; never truncate a sentence.
- **R8.3** Do not silently clip content: truncate with access to the full value, wrap, or
  scroll.
- **R8.4** Identifiers, measurements and columns of numbers use tabular figures.

## R9 · Stability

- **R9.1** Reserve the space used by errors, hints, progress and status. A message never moves
  the fields or buttons that follow it.
- **R9.2** Buttons confirm pending, success and failure in place, at a stable width.
- **R9.3** Skeletons match the loaded geometry box for box.
- **R9.4** Live updates patch values in place; a changed value may flash its own cell.
- **R9.5** Scroll containers reserve their scrollbar gutter, so content never jumps sideways.
- **R9.6** Hover and focus never change a control's size or position.

## R10 · Loading

- **R10.1** Load inside the affected region. Do not show page-level or full-screen progress;
  the shell renders while data loads.
- **R10.2** A spinner fades in only when work outlasts `--spinner-delay`.
- **R10.3** Large features (maps, syntax highlighting, charts in results) load on demand
  behind a placeholder of the right size.

## R11 · Interaction

- **R11.1** Base UI owns keyboard navigation, focus, positioning and ARIA behaviour; shared
  recipes own hover, press, focus and disabled states. Links use the same grammar.
- **R11.2** Every pointer action has a keyboard path, and every keyboard path has a visible
  focus ring.
- **R11.3** An unavailable action explains why. It stays focusable (`aria-disabled`) and shows
  the reason in its tooltip and description.
- **R11.4** Focus shows the control halo and keeps the material's elevation.
- **R11.5** Composite widgets are one tab stop; arrow keys move within them. Context menus also
  open with Shift+F10 and the Menu key.
- **R11.6** A row's ⋯ menu and its context menu are the same menu, built from the same
  definition.
- **R11.7** Row actions appear on hover and focus, and always on touch.
- **R11.8** Selection follows the platform: checkboxes, Shift-click ranges, ⌘/Ctrl-click
  toggles.
- **R11.9** Tones mean the same thing on buttons, badges, notices and status dots.
- **R11.10** Nothing clips a focus ring. A container that clips (it scrolls or hides
  overflow) keeps `--focus-reach` between its edge and the controls inside it: give it
  `fa-focus-room`, add `var(--focus-reach)` to its own padding, or, where it clips only to
  truncate text or round its corners, use `overflow: clip` with
  `overflow-clip-margin: var(--focus-reach)`. A clipped flex or grid item then needs
  `min-width: 0`, which `overflow: hidden` implied, and the margin must be a plain length
  (Chromium drops `calc()` there). Rows and cards that span a scroller take an inset ring.

## R12 · Actions

- **R12.1** Promote the most important actions to buttons and keep every action in the ⋯ menu.
  The primary action is rightmost.
- **R12.2** Action groups render in a fixed order; destructive actions come last, after a
  separator.
- **R12.3** Hide an action that never applies to the target; disable with a reason one that
  applies but is unavailable now. In a menu the row is only dimmed; the reason is its tooltip,
  beside the menu, on hover and keyboard highlight, never a caption line under the row.
- **R12.4** Confirm consequential actions with an AlertDialog that names the target and the
  outcome: “Remove NST-C106 from Northstar Studio?”.
- **R12.5** Report the result in place on the button that started it, or with a toast for bulk
  and background actions.
- **R12.6** Entity settings open in the entity's settings dialog, not a separate page per
  setting.

## R13 · Overlays

- **R13.1** Overlays emerge from their anchor and leave quickly (R18); focus returns to the
  trigger when they close. One Escape closes the topmost overlay: a tooltip showing on a
  focused control closes with it and never takes the press for itself. A dialog opened from
  the keyboard focuses its first control (a settings dialog, its current section), not the
  header close button.
- **R13.2** Settings dialogs follow one pattern: a header with icon tile, title and data
  subtitle; a rail of sections beside a scrolling pane; a pinned footer. The dialog's height
  is fixed, so switching sections never resizes it.
- **R13.3** Dialogs stack at most two deep; the parent recedes behind the child. Open a window
  for anything deeper.
- **R13.4** On phones a dialog becomes a bottom sheet with thumb-sized actions above the safe
  area.
- **R13.5** Tooltips hold one line and nothing interactive. Popovers hold small, non-blocking
  content; a menu never holds form fields.
- **R13.6** Toasts appear in the bottom corner at the reading end on desktop and at the top on phones, at most three at
  once.
- **R13.7** A dialog with unsaved changes asks before it closes.
- **R13.8** Assistant questions and approvals are never modal; they wait above the composer.
  The host supplies the authorization policy.

## R14 · Windows and background state

- **R14.1** A window is a view in a frame; its body supplies actions and live state through
  slots.
- **R14.2** Windows reconstruct from a serialisable kind and parameters registered by the host;
  the host owns storage namespaces and content.
- **R14.3** Windows can be moved and resized from the keyboard through the window menu.
- **R14.4** Windows sit above the scope: switching organisation never closes them, and a
  window from another scope shows which one it belongs to.
- **R14.5** Dragging and resizing write transforms each frame and commit state on release,
  without re-rendering content.
- **R14.6** Background state — connection, sync, queued work — lives in the status bar of the
  view it concerns, never in a banner in the body.
- **R14.7** Panning and zooming write one transform per frame.
- **R14.8** A window's tools live in its app bar. In full screen, where the app bar is gone,
  the body draws them as a floating toolbar that includes a way out of full screen.

## R15 · Forms

- **R15.1** Use TanStack Form and the typed schema helpers.
- **R15.2** One field per row.
- **R15.3** One setting per SettingRow.
- **R15.4** A boolean setting is a Switch in a setting row.
- **R15.5** Two to four short options use Segmented or radio cards; more use a Select or
  Combobox.
- **R15.6** A text-like field's width matches the value's expected length.
- **R15.7** Forms use one column at `--form-measure`.
- **R15.8** Related rows sit under an overline group label, `--gap-section` apart — space and a
  label, not a divider.
- **R15.9** Validate on blur, then on change after an error. Normalise typed input on blur so
  the caret stays put.
- **R15.10** A form saves with one Save button that stays disabled until something changes and
  confirms in place.
- **R15.11** A setting that applies at once needs no Save button: it is optimistic, confirms on
  its row and rolls back on failure.

## R16 · Data tables

- **R16.1** Sorting, filters, page and page size live in the URL. An infinite table keeps its
  sorting, filters and search there; how far it has loaded is not part of the link.
- **R16.2** Column visibility, sizing and pinning respond to the container and the column
  menu.
- **R16.3** Column widths, hidden columns, pins and density are per-user preferences. Saved
  choices take precedence; Reset columns restores the application defaults.
- **R16.4** Loading, empty and error states use the table's own box.
- **R16.5** Selecting rows shows the bulk-action bar in the status bar's place.
- **R16.6** Keep a data workspace bounded around one primary table. Project related facts into
  columns of one row; put independent datasets in separate routed tabs. Use the padded body
  slot for table compositions.
- **R16.7** Each column states how it filters, searches and sorts. The host supplies paging,
  server filters and subscriptions; never filter one page as if it were the full result.
- **R16.8** Toolbar search is one condition across the searchable columns, combined with the
  filters.
- **R16.9** Hide technical identifiers by default with `defaultHiddenColumns`; keep them in the
  column chooser and in expanded row and card details.
- **R16.10** Use stable row IDs. Manual row order belongs to the host: `reorder` reports each
  move and the host updates its data. Reordering is unavailable, with the reason shown, while
  the visible order is not the manual order.

## R17 · Live data

- **R17.1** Update loaded values in place; do not reload the view to show a change.
- **R17.2** Live work pauses when its view is hidden or off screen, and goes quiet when its
  subscription ends.
- **R17.3** New rows wait behind a count (“3 new”) instead of pushing rows under the pointer.
- **R17.4** Connection state belongs to the view it concerns (R14.6), shown with a status dot
  and its last update.

## R18 · Motion

- **R18.1** Animate transform and opacity. A disclosure's height (`fa-collapse`) is the one
  sanctioned layout animation; anything else that travels moves with a transform, or lays out
  once and animates from where it was.
- **R18.2** Nothing loops except a spinner while work is running. A streaming caret is static.
- **R18.3** Every duration multiplies by `--motion-scale`. Under Still (`data-motion="reduced"`)
  or the operating system's reduced-motion setting nothing moves; script reads the same switch
  through `prefersReducedMotion()`, `motionScale()` and `tokenDuration()`.
- **R18.4** Motion is physical and shared: indicators glide (`fa-glide`), presses spring back
  (`fa-pressable`), overlays materialise from their anchor (`fa-popup`) on the spring tokens
  and leave on the exit tween. List rows highlight at once and fade as they leave.
- **R18.5** Never update React state per pointer frame or per animation frame; write styles to
  the moving element and commit at the end.

## R19 · Icons

- **R19.1** Components size their icons; pass icons without a size.
- **R19.2** Navigation icons (Rail, TabBar, section lists) use the large size.
- **R19.3** Icons come from `glass-ux/icons` and follow the [icon specification](icon-spec.md).
  A brand mark is not an icon; company icons identify the named service only.

## R20 · Accessibility

- **R20.1** Meet WCAG 2.2 AA in both modes, every palette and every material: 4.5:1 for text,
  3:1 for graphics and focus indicators. Inactive (disabled) controls are exempt from the 3:1
  non-text requirement, as in WCAG 2.2 SC 1.4.11, but must still read as visibly quieter than
  their active form.
- **R20.2** Preserve accessible names, roles and states when a control changes form.
- **R20.3** Return focus to the control that opened an overlay, and to a sensible neighbour
  when the focused element is removed.
- **R20.4** Touch targets are at least `--target-min`; small controls extend their hit area
  without growing.
- **R20.5** Every icon-only control and status icon names itself, including its state.
- **R20.6** A scrolling region that is not otherwise focusable is keyboard scrollable.
- **R20.7** Icon-only buttons always have a tooltip; solid fills always use their paired
  foreground.
- **R20.8** Count badges on a tile use the solid, ringed overlay so they read on any surface.
- **R20.9** Announce outcomes with polite live regions that stay mounted, so the first message
  is not lost.
- **R20.10** Forced colours (Windows High Contrast): every control keeps a visible boundary
  (`ButtonText` or `CanvasText` borders, transparent borders that the system colours), focus
  is an outline in `Highlight`, selected, checked and current states use `Highlight` and
  `HighlightText` or a `Highlight` border rather than a fill alone, disabled controls use
  `GrayText`, icons use `currentColor`, and materials become `Canvas` with a border. Status
  carried by colour alone (a ToneDot, a chart series) keeps a shape or a label. Components
  get this from `src/styles/forced-colors.css`; a host's own controls follow the same
  pattern and are checked with forced colours emulated.

## R21 · Phones and touch

- **R21.1** The shell switches layouts at its breakpoints; everything else adapts to its
  container.
- **R21.2** At the narrowest width an ActionBar becomes one ⋯ menu on the title line.
- **R21.3** Primary content and actions stay in the first screen on a phone.
- **R21.4** Hover is an enhancement: everything reachable by hover is reachable by tap.

## R22 · Using the library

- **R22.1** Import each component from its own entry (`glass-ux/button`), not from `glass-ux`.
  Only the entries listed in the package's `exports` resolve; internal module paths such as
  `glass-ux/ui/button/button` do not.
- **R22.2** Mount `AppearanceProvider`, `TooltipProvider`, `ActionProvider` and
  `PaletteProvider` once at the application root when using their components.
- **R22.3** Use controlled props (`value`, `onValueChange`) when the application owns the
  state, and uncontrolled defaults (`defaultValue`) otherwise; do not mix them on one control.
  Single selection follows the same pattern: `selectedId`, `defaultSelectedId` and
  `onSelectedIdChange(id, details)` on Tree, TopologyCanvas, GeoMap and SessionNav.
- **R22.4** Pass stable callbacks and objects to hot components (table rows, cells, charts) so
  memoised rows do not re-render needlessly.
- **R22.5** Read the documentation installed with the package version you use; agent skills
  in `skills/` match that release.
- **R22.6** Check the changelog and [migration guide](migration.md) before upgrading, and
  replace deprecated names before the release that removes them.

## R23 · Authentication

- **R23.1** Use `LoginFlow` for sign-in, provider sign-in, password reset, account creation and
  two-factor steps. The host owns every backend contract, URL and brand.
- **R23.2** Do not reveal whether an account exists: reset requests and refusals use the same
  wording for known and unknown identifiers.
- **R23.3** Show refusals the person can act on; send unexpected errors to `onError`, never to
  the screen.
- **R23.4** Use the correct `autocomplete` tokens (`username`, `current-password`,
  `new-password`, `one-time-code`) so password managers work.

## R24 · Ownership and verification

- **R24.1** Applications own install metadata, authentication, authorization and runtime
  policy. Library components stay free of application branding, business entities and backend
  contracts; adapters for a specific server live under `glass-ux/adapters/*`.
- **R24.2** A component has its own source folder, public typed exports, TSDoc, an API page,
  live examples with fictional data and relevant tests.
- **R24.3** Run `pnpm check`, `pnpm docs:build` and the affected browser tests. Verify density,
  UI scale, radius, line weight, actual insets and scroll edges in light, dark, Solid and phone
  layouts; rendering and axe checks alone do not establish layout correctness.
- **R24.4** A release records its changes in `CHANGELOG.md`; a breaking change also gets
  upgrade steps in the migration guide and deprecated aliases for one release where possible.

## Before you ship

A short checklist for people and agents composing a screen:

1. First screen: primary content and actions visible on desktop and phone; no repeated route
   title, slogan or explanatory paragraph.
2. Materials: one blurred layer at a time; panels and cards from Surface and Panel props.
3. Stability: errors, loading and live updates do not move buttons; skeletons match.
4. Containers: the view works from a phone column to a wide pane, and no toolbar overflows.
5. Appearance: correct in light, dark, Glass, Frosted, Solid, Still, compact density, a
   non-default UI scale, forced colours and print preview.
6. Keyboard: every action reachable, focus visible and returned, unavailable actions explain
   why.
7. Checks: `pnpm check`, `pnpm docs:build`, the affected browser tests, and
   `pnpm exec glass-ux check-layout` over the host's styles.

## Documentation layouts

The main application and its product demo use the available workspace. Component
documentation uses a centred maximum-width reading column. Stack examples vertically, follow
them with usage and the complete API, and use a vertical section rail whose links jump within
the single document. Keep every section present; do not hide them behind tab panels. Icon
demos share one Foundations page. Each chart has its own focused page.

Documentation headings, descriptions, rules and example wrappers sit on the page canvas. Code
blocks may use a well, and a component that demonstrates a surface keeps that surface. Do not
wrap every specimen in an additional card.
